Custom Memory Allocator

A low-level malloc/free implementation with splitting, coalescing, dual linked lists, and full stress-tested stability.

Links: GitHub Repository

Overview

This project is a custom implementation of malloc() and free() written entirely in C. I built it to understand how dynamic memory allocation actually works and to learn how a heap works as well. The allocator manages its own heap using sbrk(), tracks metadata for each block, and handles splitting, coalescing, and reusing freed memory.

How It Works

My allocator manages memory by dividing the heap into blocks. Each block has two parts: 

| block_header | user_memory |

The block header is internal metadata the allocator uses to track the block’s size, whether it is free or allocated, and pointers that link blocks together. The user only sees the memory portion that comes after the header.

The Two Core Data Structures

The allocator maintains two linked lists:

  • Heap list — contains every block in physical memory order. This is how the allocator finds neighboring blocks for splitting or coalescing.
  • Free list — contains only free blocks. This is where my_malloc() searches for available space.

Allocation Process (my_malloc())

When memory is requested, the allocator follows a simple flow:

  1. Align the requested size to ensure proper memory alignment.
  2. Search the free list for a block large enough to reuse.
  3. If a suitable block exists, it is returned. If not, the allocator expands the heap using sbrk() and creates a new block.
  4. If the chosen free block is larger than needed, the allocator splits it into a used portion and a smaller free block to avoid wasted space.
  5. The block is then removed from the free list and marked as allocated.
  6. Finally, the allocator returns a pointer to the user memory region (the space immediately after the metadata).

Freeing & Reuse (my_free())

When memory is freed:

  1. The pointer is moved backward to locate the block header.
  2. The block is marked as free and added back to the free list.
  3. The allocator checks neighboring blocks in the heap list. If they are also free, they are coalesced into one larger block.

This merging step is key to reducing fragmentation and ensuring the allocator can handle larger future requests without repeatedly expanding the heap.

Reusing Memory Before Growing

A major focus of the design is reuse. The allocator always consumes free blocks first, only calling sbrk() when absolutely necessary. This mirrors how real-world allocators work and minimizes operating system interactions.

The result is a lightweight allocation engine that supports splitting, coalescing, and efficient memory reuse while maintaining a clean, predictable structure internally.

Key Features

  • Manual heap expansion using sbrk()
  • Metadata headers for tracking block size and state
  • Two linked lists for efficient memory management
  • Block splitting to utilize oversized free regions
  • Coalescing to merge adjacent free blocks and reduce fragmentation
  • Aligned allocations for predictable layout and performance
  • Reusable static library (liballocator.a) built with a custom Makefile
