Custom Memory Allocator: Systems Programming Deep Dive

C · Systems Programming · Low-Level

Why Build a Memory Allocator?

I’ve called malloc() and free() many, many times, but I never really understood what happened beneath that function call. Building a custom memory allocator from scratch was my way of breaking through that abstraction. I wanted to learn how memory is actually managed, how the heap grows, why fragmentation happens, and what makes allocators fast or slow. I also really wanted to understand how the heap worked.

This project pushed me into systems programming more than any other project I've done. Manually managing memory, writing metadata structures, working with sbrk(), debugging pointer logic, and reasoning about layout at the byte level taught me a lot about how a computer works.

Designing the Allocator

Before writing any code, I drew out how a memory allocator actually works. Every allocation on the heap starts with a block header which is a small metadata struct that stores the block’s size, whether it’s free, and pointers that link blocks together.

Heap Blocks: Metadata + User Memory

Each block on the heap looks like this:

| METADATA (block_header) | USER MEMORY |

When I return a pointer from my_malloc(), I give the user a pointer to the memory immediately after the header. Later, when my_free() is called, I subtract the size of the header to recover the metadata.

Two Linked Lists: Heap List and Free List

A key design decision was to use two linked lists:

  • Heap List: Contains every block in physical address order.
  • Free List: Contains only free blocks, used for fast lookup.

This dual-list system mirrors real allocators such as dlmalloc and makes searching, splitting, and coalescing efficient.

Growing the Heap with sbrk()

When no free block can satisfy an allocation request, my allocator calls sbrk() to ask the operating system for more memory. sbrk() returns a contiguous chunk of heap space, which I wrap in a block header and insert into both lists. 

sbrk(sizeof(block_header) + requested_size);

Splitting Blocks

If a free block is larger than needed, the allocator splits it: 

[ USED BLOCK ][ NEW FREE BLOCK ]

This optimization reduces waste and keeps the heap flexible.

Freeing and Coalescing

When a block is freed, I mark it free and insert it into the free list. Then I try to merge it with neighboring free blocks which is a process called coalescing. This helps avoid fragmentation: 

[ FREE ][ FREE ] → [ BIG FREE ]

Testing the Allocator

I wrote several tests during the project, from small sanity checks to a full randomized stress test. These were the most important ones.

1. Basic Allocation Test

The very first thing I validated was whether my_malloc() actually returned safe, writable memory. I allocated a few blocks and filled them with known byte patterns: 

void* a = my_malloc(32);
void* b = my_malloc(64);

memset(a, 0xAA, 32);
memset(b, 0xBB, 64);

If these writes succeed, it means the allocator returned the correct region after the metadata header, block splitting worked, and no hidden corruption occurred. This was the first sign that the engine underneath was behaving properly.

2. Coalescing Test

Next, I tested whether free blocks merge correctly. I allocated three blocks in a row and freed them in an order that forces coalescing: 

// Allocate three adjacent blocks
a = my_malloc(32);
b = my_malloc(32);
c = my_malloc(32);

my_free(b); // free middle block
my_free(a); // should merge into [a+b]
my_free(c); // should merge into [a+b+c]

After merging, the expected size of the combined block is: 

32 + 32 + 32 + 2 * sizeof(block_header)

This test uncovered one of the trickiest bugs in the entire project.

3. Full Randomized Stress Test

Once splitting and coalescing worked in isolation, I stress-tested the entire allocator using thousands of random allocation and free operations. In this test, I repeatedly allocated blocks of random sizes, freed them in unpredictable orders, and constantly validated the heap and free list for structural correctness: 

for (int i = 0; i < 5000; i++) {
    if (rand() % 2) {
        void* p = my_malloc(random_size());
        memset(p, 0xAB, size); // ensure memory is writable
        ptrs[count++] = p;
    } else if (count > 0) {
        int idx = rand() % count;
        my_free(ptrs[idx]);
        ptrs[idx] = ptrs[count - 1];
        count--;
    }

    validate_heap();
    validate_free_list();
}

The Coalescing Bug I Found

During the coalescing test, the heap list looked perfect—all three blocks merged exactly as they should. But the free list still showed a block of size 32 instead of the full merged size of 192 (32 + 32 + 32 for each block's user memory plus 48 + 48 + 48 for each block's metadata).

The issue? I updated the heap list correctly during merges, but I wasn’t updating the free list to reflect those changes.

In a backward merge, the “current” block disappears and the previous block becomes the new merged block. But I was still leaving the old block inside the free list, which meant the free list and heap list were out of sync. Later merges had no chance of working correctly.

Once I updated coalesce() to return the new merged block and reinsert it properly into the free list, everything snapped into place: 

block = coalesce(block);

After that fix, both the coalescing test and the full randomized stress test passed with zero errors. The heap and free list now stay perfectly synchronized, no matter what allocation pattern I throw at it.

What I Learned

Memory Management Fundamentals

This project made me really understand what’s actually going on behind malloc() and free(), and how closely user memory sits next to the allocator’s own bookkeeping. I learned why fragmentation happens, how splitting and coalescing fix it, and honestly, finally understanding how it all works was pretty cool.
