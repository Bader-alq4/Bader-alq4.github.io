Building a Production-Level Full Stack System

Web Systems · Backend Architecture · Authentication · Payments

Why I Built This

Before this project, most information lived on Instagram. Tryouts, schedules, updates were scattered across posts, stories only, and there was no single place people could rely on for information.

I originally set out to fix that with a simple website where players and parents could find accurate information. But once I started, I realized this was a good opportunity to go deeper.

I expanded the project into a full backend system so I could learn how real production systems are actually built. Even though not every feature is actively used today, everything was designed, implemented, and tested end to end.

This project became my way of understanding how modern web systems work under real constraints.

How the Application Works Internally

At a high level, the system follows a standard client–server model. A React frontend sends HTTP requests to an Express backend. The backend handles authentication, validation, business logic, and database access.

Thinking about how a single request flows through the system helped me reason about bugs, security issues, and production behavior.

Server entry point

The backend starts in server.js. This file is responsible for bootstrapping the application. It loads environment variables, connects to the database, and starts the HTTP server.

The Express app itself lives in app.js. Separating startup logic from the app definition made testing easier and kept configuration concerns isolated from runtime behavior.

Global middleware and request handling

Every request passes through a shared middleware pipeline before it ever reaches a route handler. This includes JSON parsing, logging, security headers, CORS configuration, and rate limiting on sensitive endpoints.

Middleware order matters. Authentication must run before protected routes. Validation must run before controller logic. Thinking in terms of a request pipeline helped me avoid subtle bugs. 

Request
→ middleware
→ authentication
→ validation
→ controller
→ database
→ response

Routing and controllers

Routes are grouped by feature area such as authentication, tryouts, payments, and admin actions. Routes define the HTTP method and path, but contain very little logic themselves.

Business logic lives in controllers. Controllers assume authentication and validation have already run. This separation kept responsibilities clear and made the codebase easier to extend over time.

Authentication flow in practice

For protected routes, the client sends an access token in the Authorization header. Middleware verifies the token, checks expiration, and attaches the user to the request.

If the token is missing or invalid, the request is rejected immediately. Unauthorized requests never reach sensitive code paths.

Error handling and status codes

Controllers return appropriate HTTP status codes based on the outcome of each request. Invalid input returns 400-level errors. Authentication failures return 401 or 403.

Centralized error handling keeps responses consistent and makes frontend behavior more predictable.

Local development vs deployment

Many issues don’t show up locally. Once deployed, browser security rules, cookies, CORS, and environment variables behave differently.

I had to explicitly configure allowed origins, enable credentials for refresh tokens, and double-check environment-specific settings. It was extremely tedious but it reinforced how important it is to test projects when they're deployed, not just locally.

Authentication and Sessions

I implemented authentication using JSON Web Tokens to understand how stateless auth works in practice. The system uses two tokens.

Access tokens are short-lived and sent with every protected request. Refresh tokens are long-lived and stored in httpOnly cookies.

This setup balances security and user experience. Access tokens are fast to verify. Refresh tokens allow sessions to persist without forcing users to constantly log in again. 

Authorization: Bearer <access_token>

When an access token expires, the client automatically calls a refresh endpoint. If the refresh token is valid, a new access token is issued and the original request is retried.

Authorization and Roles

Authentication and authorization are separate concerns. Being logged in does not automatically mean you can do everything.

Sensitive routes check both token validity and user role. Admin-only routes are protected on the backend, not just hidden in the UI.

Frontend checks improve UX. Backend checks are what actually provide security.

HTTP, CORS, and Security

Because the frontend and backend are deployed separately, I had to deal with cross-origin requests. CORS is explicitly configured to allow only the frontend origin and support credentials.

I also added basic security layers: request logging, rate limiting on auth routes, and HTTP headers to reduce common attack vectors.

Payments and Webhooks

Even though payments aren’t currently used, I fully implemented Stripe to understand real-world payment flows.

The key lesson was that the frontend is never the source of truth for payments. Stripe webhooks are.

After checkout, Stripe sends an event to the backend. The backend verifies the signature, validates the amount and currency, and only then updates the database.

This prevents payments from being faked through frontend manipulation.

What I Took Away From This

The biggest thing I learned from this project was how to think about building a full stack system from start to finish.

I stopped thinking only in terms of code and started thinking about how a real user would interact with the system. What they expect to work. What feels slow. What breaks when something unexpected happens.

The way I test things changed as well. I started testing flows the way a user would use them instead of only checking that endpoints returned the right data. I tried actions out of order and paid more attention to edge cases.

I also got much better at reading documentation. Features like payments forced me to rely on official docs instead of examples. Working through Stripe documentation taught me how to understand real APIs and implementation details.
